# Conduit E2E tests: Playwright MCP vs playwright-cli

The same manual test case — **"Create a new article"** on [Conduit](https://conduit.bondaracademy.com/) (the RealWorld demo app) — automated **twice**: once through **Playwright MCP** and once through **playwright-cli**. The point of the project is the comparison: what changes when the agent drives the browser through MCP tools versus through shell commands and a skill.

**Status: 3 tests, all passing** (verified twice in a row on 2026-09-23). The suite needs a live connection to the public demo site.

## The comparison

### 1. Both tools produce the *same* snapshot — the difference is what reaches the model

Both Playwright MCP and playwright-cli work off the **accessibility tree**, not the DOM and not pixels. On the same page they produce the same shape of snapshot with element refs (`f1e…` for MCP, `e1…` for CLI) — a full-page snapshot of the Conduit home page is roughly **360 lines** in both.

Measured on this project's own artifacts, which are kept out of git:

| | Playwright MCP | playwright-cli |
|---|---|---|
| Snapshot artifacts on disk | 21 `.yml` + 3 `.log` — 121.9 KB total, 5.1 KB average | 15 `.yml` + 2 `.log` — 78.7 KB total, 4.6 KB average |

The size difference comes from *how the workflow reads the page*: the CLI workflow leans on targeted reads (`find`, `snapshot --depth=4`, `snapshot e34`, `eval`), so many of its snapshots are partial and small, while MCP `browser_snapshot` returns the whole tree inline.

**This is the actual cost difference**, and it is not about the files: files on disk are free until something reads them. What is billed is context — and MCP charges a fixed cost for its tool schemas on every request, plus the full snapshot after each call, whereas the CLI charges only for the concise command output.

### 2. The debug-session lifecycle (the trap that costs an hour)

`playwright test --debug=cli` pauses a test and hands you a session name (`tw-XXXX`). Attaching to it gives you `pause-at`, `step-over` and `resume` — but:

- `playwright-cli resume` runs the test to the end, the runner closes the browser, and the session dies;
- `playwright-cli step-over` executes the next statement (for example the seed's `page.goto`) and leaves the test paused — the browser stays alive, so you can walk the scenario interactively.

The working pattern is therefore: start the test in the background, `attach`, `step-over` once, and only then explore.

### 3. Generation details worth knowing

- The CLI generates `.first()` where a locator matches several elements (for example "Delete Article", which appears twice on the details page). That is a hint to make the locator explicit rather than a finished answer.
- Font Awesome icons end up inside accessible names (for example `" New Article"`). Replacing them with a regular expression is part of healing the generated test.
- The minimal CLI generation prompt is about ten lines: name the skill, forbid MCP browser tools, give the target file, and tell the agent not to overwrite the reference test. Everything else comes from the skill and the live application.

The scenarios sign in with a shared demo account. Override the defaults instead of editing the tests:

```bash
CONDUIT_EMAIL=you@example.com CONDUIT_PASSWORD=secret npm test
```

## What running the suite in parallel taught us

The first run in this repository was red — and the reason was not a broken locator:

```
1 failed  create-new-article-cli.spec.ts  › Create a new article
  Locator: locator('.article-preview').first().getByRole('heading', { name: 'PW CLI Article 1790170389542' })
  Error: element(s) not found
```

The manual test case asks to verify that **the first article in the feed** is the one just created. That holds for a single user acting alone, but the two scenarios share one account and run in parallel: while one test publishes its article, the other publishes its own, so "first" can belong to the other test. Run in isolation, the same test passed.

**Fix:** both scenarios now assert that *an article preview carrying the created title* is present and open it, instead of depending on its position in the feed. The suite has been green in repeated parallel runs since. This is a good illustration of the general rule: a test that shares remote state with another test cannot rely on global ordering.

## Known limitations

- **The suite mutates shared public data.** Each scenario creates a real article on the public demo site and deletes it at the end, so a scenario that fails before its delete step leaves the article behind. The project therefore deliberately has **no CI workflow**: running it on every push would hammer a third-party service and pollute its feed with abandoned articles.
- **The suite depends on a live third-party site and a shared account.** If the demo site changes or the account is unavailable, the tests fail for reasons unrelated to this code.
- The backlog in `specs/conduit.plan.md` lists the scenarios that are planned but not automated yet (sign-in validation, editing an article, comments).

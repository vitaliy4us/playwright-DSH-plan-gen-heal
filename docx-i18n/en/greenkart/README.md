# GreenKart end-to-end tests with Playwright Test Agents

[![Playwright tests](https://github.com/vitaliy4us/playwright-DSH-plan-gen-heal/actions/workflows/playwright.yml/badge.svg)](https://github.com/vitaliy4us/playwright-DSH-plan-gen-heal/actions/workflows/playwright.yml)

End-to-end test suite for the [GreenKart](https://rahulshettyacademy.com/seleniumPractise/#/) demo shop, produced with the Playwright Test Agents workflow: a **planner** writes a Markdown test plan, a **generator** turns the plan into Playwright tests, and a **healer** repairs failing tests.

**23 tests — 21 passing, 2 marked `test.fixme()` because they document confirmed application defects** (see [Bug Reports](Bug%20Reports)).

---

## What is in the repository

| Path | Purpose |
|---|---|
| `specs/` | Human-readable Markdown test plans — the source of truth for what is covered |
| `tests/` | Playwright specs, one test per file, grouped by feature |
| `tests/seed.spec.ts`, `tests/fixtures.ts` | Seed test and the fixture that opens the application, so no test repeats the navigation |
| `Test Cases/` | Manual test cases (step / expected result / actual result tables) |
| `Bug Reports/` | Defects found while testing, with manual reproduction steps and evidence |
| `.agents/skills/` | Role skills (`playwright-test-planner`, `playwright-test-generator`, `playwright-test-healer`) that give a coding agent the three roles |
| `.github/agents/` | Playwright agent definitions, generated by `npx playwright init-agents` |
| `SESSION-NOTES.md` | Running memory of the project: decisions, findings, environment quirks |

## How the tests were produced

1. **Plan** — the planner explores the application and writes a Markdown plan (`specs/*.md`) with groups, scenarios, steps and expected results.
2. **Generate** — the generator executes each scenario live in a browser and writes the Playwright test from what actually worked, one test per file.
3. **Heal** — the healer runs the suite, reproduces failures, finds the root cause and applies the minimal fix.

Defects found this way are not "fixed" by weakening a test: a failing test that reflects correct expectations is marked `test.fixme()` and reported in [`Bug Reports/`](Bug%20Reports), while tests that document the current (defective) behaviour stay green on purpose, so a change in the application is noticed.

The agent definitions in `.github/agents/` are generated by Playwright and should be regenerated after upgrading:

```bash
npx playwright init-agents --loop=vscode     # or: claude | codex | opencode
```

## Getting started

```bash
npm ci
npx playwright install --with-deps chromium
npm test
```

| Script | What it does |
|---|---|
| `npm test` | Run the whole suite |
| `npm run test:headed` | Run with a visible browser |
| `npm run test:ui` | Run in Playwright UI mode |
| `npm run report` | Open the last HTML report |
| `npm run trace` | Open a trace file in the trace viewer |

## Defects found by the suite

| Report | Summary |
|---|---|
| [BUG-1](Bug%20Reports/BUG-1-cart-is-lost-on-immediate-reload.md) | The cart is flushed to `localStorage` about one second after a change, so a reload issued immediately after "ADD TO CART" races that write and loses the cart. Verified test: `tests/cart-edge-cases/should-persist-cart-after-app-reload.spec.ts` (`test.fixme`). |
| [BUG-2](Bug%20Reports/BUG-2-empty-cart-can-be-ordered.md) | No validation blocks the checkout flow with an empty cart: the whole flow can be completed and the application returns to the shop as if an order had been placed. Expected behaviour asserted by `tests/cart-edge-cases/should-not-offer-order-placement-when-the-cart-is-empty.spec.ts` (`test.fixme`). |

## Notes and known constraints

- **The suite drives a live third-party site.** A red CI run can therefore mean the demo shop is slow or unavailable rather than a regression. Playwright retries twice and uses one worker on CI (`playwright.config.ts`).
- **Application quirks** are documented in the plans and in the test comments, because they are easy to get wrong: the rupee sign is rendered through CSS `::before` and is absent from the element text; the cart drawer markup exists in the DOM while the drawer is closed; the header `Items` counter counts distinct products, not the total quantity; the order confirmation screen stays visible for more than five seconds; the cart is persisted with about a one-second delay.
- **Tests are independent:** each test gets a fresh browser context, and `tests/fixtures.ts` opens the application, so no test repeats the navigation step.

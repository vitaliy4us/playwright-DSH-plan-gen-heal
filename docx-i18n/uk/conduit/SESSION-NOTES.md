## Ключові знахідки (критично для завтра)
1. **MCP vs CLI — річ не у снапшотах, а в контексті.**
   Обидва інструменти роблять ОДНАКОВИЙ accessibility-снапшот (це не DOM!): рефи `e1..`
   (CLI, файли в `.playwright-cli/`) і `f1e..` (MCP, файли в `.playwright-mcp/`), по ~360 рядків /
   ~15 КБ на головній сторінці в обох. Різниця в тому, скільки контенту потрапляє в контекст:
   MCP `browser_snapshot` віддає повне дерево інлайн; CLI-воркфлоу використовує точкові
   `find` (~13 рядків), `snapshot --depth` (~30 рядків), `eval`. Тарифікується лише контекст;
   файли на диску безкоштовні до моменту читання.
2. **Життєвий цикл сесії налагодження (`--debug=cli`).**
   `playwright-cli resume` доводить seed до кінця — раннер закриває браузер, і сесія `tw-XXXX`
   вмирає. Робочий прийом: **`step-over`** — виконує `page.goto` і залишає тест
   призупиненим на «Close context»: браузер живий, сторінка в потрібному стані → можна
   інтерактивно проходити кроки сценарію.
3. **Sandbox (важливо!).** `playwright test` (раннер форкає воркери з piped stdio → EPERM) і
   `playwright-cli` (демон пише в `%LocalAppData%\ms-playwright\daemon` → EPERM) потребують
   `danger-full-access`; ескалація разова на команду (підтверджує користувач).
4. **CLI сам генерує `.first()`** там, де локаторів кілька (Delete Article зустрічається ×2).
   Іконки Font Awesome в іменах (наприклад « New Article») краще замінювати на regex-ім'я — це
   частина «лікування».
5. **Мінімальний промпт CLI-генерації (~10 рядків):** згадати «using the playwright-cli skill» +
   «Do not use MCP browser tools» + цільовий файл + не перезаписувати еталон. Усе інше
   агент бере зі скіла та живого застосунку.
6. **Асерти в обох тестах еквівалентні:** URL `/login` і `/editor`, `.navbar` містить `pwtest`,
   URL `/article/...`, Edit/Delete `.first()` visible, блок коментарів («Write a comment...» +
   «Post Comment»), вкладка Global Feed активна (фільтр `hasText`, бо `.nav-link.active`
   збігається з 2 елементами), перша `.article-preview` = створена стаття, після видалення
   `heading` count 0. Опис статті на сторінці деталей НЕ показується — асертити body.

## План на завтра: універсальний воркфлоу planner-generator-healer
Документація скіла: `C:\Users\vital\.dsh\skills\playwright-cli\references\test-generation.md`
1. **Planner** — `specs/<feature>.plan.md`: сценарії (для conduit: вхід, CRUD статті,
   коментарі), кожен зі структурою Seed / кроки / `- expect:`.
2. **Generator** — на кожен сценарій: `PLAYWRIGHT_HTML_OPEN=never npx playwright test
   tests/seed.spec.ts --debug=cli` (фон) → `playwright-cli attach tw-XXXX` → `step-over` →
   прохід кроків (`find`/`fill`/`click`) → збирання блоків «Ran Playwright code» →
   `tests/<scenario>.spec.ts`.
3. **Healer** — запуск усіх тестів, лікування падінь по одному (debug + attach), звірка зі spec.
4. **Контрольний замір** витрат токенів MCP vs CLI на однаковому сценарії.

## Головне: набір був червоним, і це виявився дефект проєктування тесту

Перший запуск після місячної перерви: **2 passed, 1 failed**. Упав `create-new-article-cli.spec.ts` на кроці 6:
«перша стаття у стрічці — та, що я створив» → `element(s) not found`.

**Діагноз.** Обидва сценарії йдуть **паралельно на одному спільному акаунті**: поки один публікує свою статтю,
інший публікує свою, тому «перша у стрічці» може виявитися чужою. Перевірка гіпотези: той самий тест
окремо — **1 passed за 5.8 с**. Тобто річ не в локаторі й не в застосунку.

**Фікс (в обох файлах).** Асертимо не позицію, а сам факт: шукаємо превʼю із заголовком створеної статті
(`.article-preview` + `filter({ hasText: articleTitle })`) і відкриваємо його. Запуск двічі підряд — **3 passed**
щоразу. Загальний висновок: тест, який ділить віддалений стан з іншим тестом, не може спиратися на
глобальний порядок.

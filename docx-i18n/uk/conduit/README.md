# E2E-тести Conduit: Playwright MCP проти playwright-cli

Той самий ручний тест-кейс — **"Create a new article"** на [Conduit](https://conduit.bondaracademy.com/) (демо-застосунок RealWorld) — автоматизовано **двічі**: один раз через **Playwright MCP** і один раз через **playwright-cli**. Сенс проєкту — у порівнянні: що змінюється, коли агент керує браузером через інструменти MCP, а що — через shell-команди та скіл.

**Статус: 3 тести, усі проходять** (перевірено двічі підряд 2026-09-23). Набору тестів потрібне живе з'єднання з публічним демо-сайтом.

## Порівняння

### 1. Обидва інструменти створюють *однаковий* снапшот — різниця в тому, що доходить до моделі

І Playwright MCP, і playwright-cli працюють на основі **дерева доступності** (accessibility tree), а не DOM і не пікселів. На одній і тій самій сторінці вони створюють снапшот однакової форми з рефами елементів (`f1e…` для MCP, `e1…` для CLI) — снапшот усієї сторінки головної Conduit — приблизно **360 рядків** в обох.

Виміряно на власних артефактах цього проєкту, які не додаються до git:

| | Playwright MCP | playwright-cli |
|---|---|---|
| Артефакти снапшотів на диску | 21 `.yml` + 3 `.log` — 121,9 КБ загалом, у середньому 5,1 КБ | 15 `.yml` + 2 `.log` — 78,7 КБ загалом, у середньому 4,6 КБ |

Різниця в розмірі походить із *того, як воркфлоу читає сторінку*: CLI-воркфлоу спирається на точкові читання (`find`, `snapshot --depth=4`, `snapshot e34`, `eval`), тому багато його снапшотів часткові й малі, тоді як MCP `browser_snapshot` повертає все дерево інлайн.

**Ось у чому справжня різниця у витратах**, і вона не про файли: файли на диску безкоштовні, доки їх щось не прочитає. Тарифікується контекст — і MCP стягує фіксовану плату за схеми своїх інструментів у кожному запиті, плюс повний снапшот після кожного виклику, тоді як CLI стягує плату лише за стислий вивід команди.

### 2. Життєвий цикл сесії налагодження (пастка, що коштує годину)

`playwright test --debug=cli` зупиняє тест і видає вам ім'я сесії (`tw-XXXX`). Приєднання до неї дає `pause-at`, `step-over` і `resume` — але:

- `playwright-cli resume` доводить тест до кінця, раннер закриває браузер, і сесія вмирає;
- `playwright-cli step-over` виконує наступний оператор (наприклад, `page.goto` із seed) і залишає тест призупиненим — браузер лишається живим, тож ви можете проходити сценарій інтерактивно.

Робочий патерн, отже, такий: запустіть тест у фоні, виконайте `attach`, один раз `step-over` — і лише потім досліджуйте.

### 3. Деталі генерації, які варто знати

- CLI генерує `.first()` там, де локатор збігається з кількома елементами (наприклад "Delete Article", який на сторінці деталей зустрічається двічі). Це підказка зробити локатор явним, а не готове рішення.
- Іконки Font Awesome потрапляють усередину доступних імен (наприклад `" New Article"`). Заміна їх на регулярний вираз — частина лікування згенерованого тесту.
- Мінімальний промпт генерації через CLI — близько десяти рядків: назвати скіл, заборонити браузерні інструменти MCP, вказати цільовий файл і сказати агенту не перезаписувати еталонний тест. Усе інше береться зі скіла та живого застосунку.

## Як запускати

```bash
npm ci
npx playwright install chromium
npm test
```

| `npm run report` | Відкриває останній HTML-звіт |

### Облікові дані

Сценарії виконують вхід зі спільним демо-акаунтом. Перевизначайте значення за замовчуванням замість редагування тестів:

```bash
CONDUIT_EMAIL=you@example.com CONDUIT_PASSWORD=secret npm test
```

## Чого навчив паралельний запуск набору

Перший запуск у цьому репозиторії був червоним — і причина була не в зламаному локаторі:

```
1 failed  create-new-article-cli.spec.ts  › Create a new article
  Locator: locator('.article-preview').first().getByRole('heading', { name: 'PW CLI Article 1790170389542' })
  Error: element(s) not found
```

Ручний тест-кейс вимагає перевірити, що **перша стаття у стрічці** — саме щойно створена. Це справедливо для одного користувача, який діє сам, але обидва сценарії використовують один спільний акаунт і виконуються паралельно: поки один тест публікує свою статтю, інший публікує свою, тож "перша" може належати іншому тесту. Запущений окремо, той самий тест проходив.

**Виправлення:** тепер обидва сценарії перевіряють, що *присутнє превʼю статті із заголовком створеної статті*, і відкривають його, замість того щоб залежати від його позиції у стрічці. Відтоді набір залишається зеленим у повторних паралельних запусках. Це добра ілюстрація загального правила: тест, який ділить віддалений стан з іншим тестом, не може покладатися на глобальний порядок.

## Відомі обмеження

- **Набір змінює спільні публічні дані.** Кожен сценарій створює справжню статтю на публічному демо-сайті й видаляє її наприкінці, тож сценарій, який падає до свого кроку видалення, залишає статтю на сайті. Тому в проєкті свідомо **немає CI-воркфлоу**: запуск на кожен push бив би по сторонньому сервісу й засмічував його стрічку покинутими статтями.
- **Набір залежить від живого стороннього сайту та спільного акаунта.** Якщо демо-сайт зміниться або акаунт стане недоступним, тести падатимуть із причин, не пов'язаних із цим кодом.
- Беклог у `specs/conduit.plan.md` перелічує сценарії, які заплановані, але ще не автоматизовані (валідація входу, редагування статті, коментарі).

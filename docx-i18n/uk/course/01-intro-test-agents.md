## 0. Що ти вмітимеш після цього уроку

1. Пояснювати різницю між «MCP-автоматизацією» та «агентною петлею» Playwright.
2. Розуміти, навіщо потрібні три агенти і як вони передають роботу один одному.
3. Знати, які артефакти залишаються в репозиторії після кожного кроку.
4. Розуміти, чому seed-тест — фундамент усього циклу.
5. Запускати весь цикл у своєму проєкті усвідомлено, а не «навмання».

## 1. Головна ідея: що змінилося в Playwright 1.56

До 1.56 у нас був **Playwright MCP** — сервер, який дає ШІ-агенту «руки» в браузері: відкрити сторінку, клікнути, ввести текст, зняти снапшот. Це потужно, але в MCP-режиму є принципова властивість: **результат роботи живе рівно стільки, скільки триває розмова**. Агент клікав, відповідав, і все це зникало в історії чату. Жодного довговічного артефакту в репозиторії не з'являлося.

Починаючи з 1.56 Playwright постачає **три Test Agents з коробки** — і вони працюють не «в чаті», а **в репозиторії**:

| | Playwright MCP | Playwright Test Agents |
|---|---|---|
| Що робить | досліджує та клікає за твоєю командою | проходить цикл і **створює файли** |
| Що залишається після | текст у чаті | `specs/*.md` + `tests/*.spec.ts` |
| Чи можна перезапустити | ні, треба повторювати промпт | так, це звичайні Playwright-тести |
| Хто веде процес | людина веде агента | людина задає мету, агенти ведуть цикл |
| Роль ШІ | «помічник із браузером» | «інженер, який залишає артефакти» |

Ключова фраза з документації: агентів **можна використовувати незалежно, послідовно або як ланки однієї агентної петлі**. Саме послідовне використання дає покриття продукту тестами.

### Агентна петля

```
   ┌──────────────────────────────────────────────────────────────┐
   │                                                              │
   ▼                                                              │
🎭 planner ──► specs/*.md ──► 🎭 generator ──► tests/*.spec.ts ──► 🎭 healer
(досліджує      (план           (пише тести       (запускає
 застосунок)     для людей)      у браузері)       і лікує)
```

Читається так: **планувальник досліджує** застосунок і пише людиночитаний план → **генератор** перетворює план на виконувані тести → **хілер** запускає їх і лікує падіння. Пунктирна стрілка назад — це heal-ітерація: доки тест не пройде (або доки хілер не вирішить, що зламана сама функціональність).

## 2. Три агенти за одну хвилину

| Агент | Що робить | Вхід | Вихід |
|---|---|---|---|
| 🎭 **planner** | досліджує застосунок і складає план тестування | чіткий запит (наприклад, «склади план для гостьового чекауту»), **seed-тест**, опційно PRD | Markdown-план у `specs/basic-operations.md` |
| 🎭 **generator** | перетворює план на виконувані тести, **перевіряючи селектори й асерти наживо** | Markdown-план із `specs/` | набір тестів у `tests/` |
| 🎭 **healer** | запускає набір і автоматично ремонтує тести, що падають | ім'я тесту, що падає | тест, що проходить, **або** `test.fixme()`, якщо, на думку хілера, зламана сама функціональність |

Зверни увагу на асиметрію входів: планувальнику потрібен **контекст середовища** (seed), генератору — **план**, хілеру — **факт падіння**. Це і є розподіл праці: дослідження → виробництво → ремонт.

## 3. Встановлення: `init-agents`

Агенти додаються в проєкт однією командою. Вона розкладає **визначення агентів** у репозиторій:

```bash
# вибери свій цикл (loop)
npx playwright init-agents --loop=vscode     # VS Code / GitHub Copilot
npx playwright init-agents --loop=claude     # Claude Code (subagents)
npx playwright init-agents --loop=codex      # Codex
npx playwright init-agents --loop=opencode   # OpenCode
```

Перед цим варто оновити сам Playwright:

```bash
npm install -D @playwright/test@latest
```

> ⚠️ **Правило, яке легко забути:** визначення агентів потрібно **регенерувати після кожного оновлення Playwright** — так підхоплюються нові інструменти та нові інструкції. Визначення постачає Playwright, а не ти.

### Що таке «визначення агента» насправді

З документації: *«agent definitions are collections of instructions and MCP tools»* — тобто це **markdown-файл з інструкціями + список MCP-інструментів**, якими агенту дозволено користуватися. Кожен агент — це не «магія», а промпт-інструкція плюс обмежений набір інструментів.

Подивись на визначення планувальника зі свого проєкту (`.github/agents/playwright-test-planner.agent.md`):

```yaml
---
name: playwright-test-planner
description: Use this agent when you need to create comprehensive test plan for a web application or website
tools:
  - search
  - playwright-test/browser_navigate
  - playwright-test/browser_click
  - playwright-test/browser_snapshot
  # ... ще інструменти браузера ...
  - playwright-test/planner_setup_page
  - playwright-test/planner_save_plan
model: Claude Sonnet 4.6
mcp-servers:
  playwright-test:
    type: stdio
    command: npx
    args: [playwright, run-test-mcp-server]
---
```

Три висновки з цього файлу:

1. **MCP усе ще всередині.** Агенти не скасовують MCP — вони його використовують. Просто тепер MCP-сервер запускається не «вручну», а як частина визначення агента: `npx playwright run-test-mcp-server`.
2. **Інструменти обмежені за ролями.** У планувальника немає `test_run` — він не запускає тести, він досліджує. У хілера немає `planner_save_plan` — він не пише плани, він лікує. Це захист від «розповзання» ролей.
3. **Є спеціальні інструменти.** `planner_setup_page` / `planner_save_plan` у планувальника, `generator_setup_page` / `generator_read_log` / `generator_write_test` у генератора, `test_run` / `test_debug` у хілера. Саме вони перетворюють «балачки з браузером» на конвеєр з артефактами.

### Про рядок `model: Claude Sonnet 4.6` — важливе уточнення

Ти помітив у визначенні агента `model: Claude Sonnet 4.6` і слушно спитав, до чого тут Claude, якщо підписки на Claude Code немає. Розбираємося за вихідниками Playwright (`lib/agents/generateAgents.js`) — і картина така:

| Цикл (`--loop`) | Що потрапляє у файл визначення |
|---|---|
| `copilot` / `vscode` | `model: Claude Sonnet 4.6` — **захардкоджено в генераторі Playwright**, не береться зі специфікації агента |
| `claude` | `model:` береться з внутрішньої специфікації агента (те саме значення) |
| `codex` | **поля `model` немає взагалі** — модель обирає хост |
| `opencode` | **поля `model` немає взагалі** — модель обирає хост |

Висновок, який знімає питання: **`model:` — це атрибут конкретної цільової платформи, а не частина логіки агента.** Він існує рівно для тих інструментів, які вміють обирати модель «на агента» (GitHub Copilot / Claude Code). Codex і OpenCode його не пишуть, бо в них модель задається хостом. Те саме в DSH: модель задається **налаштуваннями DSH**, а не файлом агента, тому рядок `model: Claude Sonnet 4.6` у `.github/agents/*.agent.md` для тебе **інертний** — його можна ігнорувати (але не видаляти вручну: файли регенеруються командою `init-agents`).

Що реально переноситься в будь-яке середовище, включно з DSH:

1. **текст інструкцій** агента (хто він і як працює);
2. **список MCP-інструментів**, які йому дозволені;
3. **сам MCP-сервер** — `npx playwright run-test-mcp-server`;
4. конвенції артефактів: `specs/` + `tests/` + `seed.spec.ts`.

Саме ці чотири речі й потрібно «пересадити» в DSH. Як саме — в [Уроці 2](02-agents-in-dsh.md).

## 4. Seed-тест — фундамент усього циклу (відео, 0:52)

Планувальнику потрібно, щоб хтось **привів застосунок у робочий стан**: залогінив, підняв фікстури, виставив залежності проєкту. Цю роль відіграє **seed test** (`tests/seed.spec.ts`) — «затравочний» тест.

```ts
// tests/seed.spec.ts
import { test, expect } from './fixtures';

test('seed', async ({ page }) => {
  // this test uses custom fixtures from ./fixtures
});
```

Що тут важливо зрозуміти:

- **Seed — це звичайний Playwright-тест.** Планувальник його *запускає*: так виконуються global setup, залежності проєктів, усі фікстури та хуки. Тобто seed приводить середовище в той стан, з якого стартують усі сценарії.
- **Seed — це ще й зразок.** Планувальник використовує його як приклад того, якими мають бути згенеровані тести (імпорти, фікстури, стиль).
- **Seed потрапляє в контекст через промпт.** У документації спеціально підкреслено: `seed.spec.ts` вказується в промпті агенту — або файлом у контексті, або згадкою імені файлу.

У твоєму проєкті `tests/seed.spec.ts` уже є — і саме він був точкою входу, коли ти проходив цикл вручну. А `tests/fixtures.ts` поряд із ним — та сама кастомна фікстура, яка відкриває застосунок, щоб кожен сценарій не починався з `page.goto`.

**Мнемоніка:** seed = «вхідні двері в застосунок». Усе, що потрібно зробити до першого кроку сценарію, живе там, а не в кожному тесті.

## 5. 🎭 Planner — досліджує та пише план (відео, 2:15)

### Вхід
- чіткий запит, наприклад: *«Generate a plan for guest checkout»*;
- seed-тест (обов'язково за змістом — він задає контекст середовища);
- опційно: продуктовий документ (PRD) для контексту.

### Що він робить під капотом

За визначенням агента його робота розбита на п'ять фаз:

1. **Navigate and Explore** — один раз викликати `planner_setup_page`, далі досліджувати інтерфейс через `browser_*`. Скриншоти робити лише за крайньої потреби (снапшот інформативніший і дешевший).
2. **Analyze User Flows** — побудувати карту основних користувацьких сценаріїв і критичних шляхів.
3. **Design Comprehensive Scenarios** — покрити happy path, **крайові випадки** та **обробку помилок**.
4. **Structure Test Plans** — кожен сценарій повинен мати: заголовок, покрокові інструкції, очікувані результати, **припущення про стартовий стан (завжди вважати, що застосунок у чистому/початковому стані)**, критерії успіху.
5. **Create Documentation** — зберегти план інструментом `planner_save_plan`.

Плюс стандарти якості: кроки мають бути настільки конкретними, щоб їх виконав будь-який тестувальник; обов'язково включати **негативні** сценарії; сценарії мають бути незалежними та запускатися в будь-якому порядку.

### Вихід: `specs/basic-operations.md`

План — **людиночитаний, але при цьому достатньо точний для генерації тестів**. Приклад із документації (TodoMVC):

```markdown
# TodoMVC Application - Basic Operations Test Plan

## Application Overview

The TodoMVC application is a React-based todo list manager ... Key features include:
- **Task Management**: Add, edit, complete, and delete individual todos
- **Bulk Operations**: Mark all todos as complete/incomplete and clear all completed todos
- **Filtering System**: View todos by All, Active, or Completed status with URL routing support
- **Real-time Counter**: Display of active (incomplete) todo count
...

## Test Scenarios

### 1. Adding New Todos

**Seed:** `tests/seed.spec.ts`

#### 1.1 Add Valid Todo

**Steps:**
1. Click in the "What needs to be done?" input field
2. Type "Buy groceries"
3. Press Enter key

**Expected Results:**
- Todo appears in the list with unchecked checkbox
- Counter shows "1 item left"
- Input field is cleared and ready for next entry
- Todo list controls become visible (Mark all as complete checkbox)
```

Зверни увагу на структуру — вона рівно та сама, що ти використовував у `specs/greenkart.plan.md`:

- **група** (`### 1. Adding New Todos`) → стане `test.describe(...)`;
- **сценарій** (`#### 1.1 Add Valid Todo`) → стане `test(...)`;
- **Steps** → стануть діями з коментарями в коді;
- **Expected Results** → стануть `expect(...)`;
- **Seed** — посилання на спільний вхід.

Це не збіг: формат плану спроєктовано так, щоб генератор міг механічно пройти «крок → виклик → асерт».

## 6. 🎭 Generator — перетворює план на тести (відео, 3:11)

### Вхід
Markdown-план із `specs/` — файл передається в контекст (або згадується за іменем у промпті).

### Як він працює (це найцікавіше)

Генератор **не пише код «з пам'яті»**. Його цикл для кожного кроку сценарію:

1. `generator_setup_page` — підняти сторінку для сценарію.
2. Для кожного кроку й перевірки: **виконати дію наживо** через інструменти браузера, використовуючи **текст кроку як намір** (`browser_click`, `browser_type`, `browser_verify_*`).
3. `generator_read_log` — забрати лог того, що реально спрацювало.
4. `generator_write_test` — одразу записати вихідний код тесту **з цього лога**.

Звідси дві речі, які пояснюють якість результату:

- **Селектори народжуються з живої сторінки, а не з фантазії моделі.** Якщо елемент знайдено наживо — він знайдеться і в тесті.
- **Документація прямо попереджає:** згенеровані тести можуть містити початкові помилки — їх лікує хілер. Це нормальний, очікуваний етап конвеєра, а не ознака поломки.

Документація також згадує, що Playwright підтримує **generation hints** і надає **каталог асертів** — щоб структурні та поведінкові перевірки були ефективними. Інструменти `browser_verify_element_visible`, `browser_verify_list_visible`, `browser_verify_text_visible`, `browser_verify_value` у визначенні генератора — саме з цього набору: агент перевіряє факт ДО того, як перетворить його на `expect`.

### Правила оформлення (жорсткі, з визначення агента)

- **один тест на файл**;
- ім'я файлу — «fs-friendly» ім'я сценарію (kebab-case);
- тест обов'язково має лежати в `describe`, **що збігається з елементом верхнього рівня плану**;
- **заголовок тесту = ім'я сценарію** з плану;
- перед кожним кроком — **коментар із текстом кроку** з плану (не дублювати, якщо крок потребує кількох дій);
- використовувати найкращі практики з лога.

### Вихід: `tests/add-valid-todo.spec.ts`

```ts
// spec: specs/basic-operations.md
// seed: tests/seed.spec.ts

import { test, expect } from '../fixtures';

test.describe('Adding New Todos', () => {
  test('Add Valid Todo', async ({ page }) => {
    // 1. Click in the "What needs to be done?" input field
    const todoInput = page.getByRole('textbox', { name: 'What needs to be done?' });
    await todoInput.click();

    // 2. Type "Buy groceries"
    await todoInput.fill('Buy groceries');

    // 3. Press Enter key
    await todoInput.press('Enter');

    // Expected Results:
    // - Todo appears in the list with unchecked checkbox
    await expect(page.getByText('Buy groceries')).toBeVisible();
    const todoCheckbox = page.getByRole('checkbox', { name: 'Toggle Todo' });
    await expect(todoCheckbox).toBeVisible();
    await expect(todoCheckbox).not.toBeChecked();

    // - Counter shows "1 item left"
    await expect(page.getByText('1 item left')).toBeVisible();

    // - Input field is cleared and ready for next entry
    await expect(todoInput).toHaveValue('');
    await expect(todoInput).toBeFocused();

    // - Todo list controls become visible (Mark all as complete checkbox)
    await expect(page.getByRole('checkbox', { name: '❯Mark all as complete' })).toBeVisible();
  });
});
```

**Розбери цей файл порядково — це еталон.** Видно: шапка з посиланнями `// spec:` і `// seed:`, один тест, `describe` = група плану, коментарі = кроки та очікування, локатори — рольові (`getByRole`), а не CSS-хаки. Саме цей скелет ти відтворював вручну в `tests/search/`, `tests/cart/` та решті папок свого проєкту.

## 7. 🎭 Healer — лікує тести, що падають (відео, 4:16)

Коли тест падає, хілер виконує чотири кроки (з документації):

1. **Replays the failing steps** — відтворює кроки, що падають.
2. **Inspects the current UI** — оглядає поточний інтерфейс у пошуку еквівалентних елементів або потоків.
3. **Suggests a patch** — пропонує патч: оновлення локатора, коригування очікування, правку даних.
4. **Re-runs the test** — перезапускає тест, доки він не пройде **або доки цикл не зупинять guardrails** (обмежувачі).

### Робочий процес за визначенням агента

1. `test_run` — запустити весь набір і знайти тести, що падають;
2. `test_debug` — для кожного падіння запустити налагодження;
3. на паузі на помилці — вивчити деталі, зняти снапшот сторінки, проаналізувати селектори, таймінги, асерти;
4. **Root Cause Analysis** — визначити першопричину: селектори, що змінилися, проблеми синхронізації, залежності від даних/середовища, зміни в застосунку, які зламали припущення тесту;
5. **Code Remediation** — полагодити код: оновити селектори, виправити асерти та очікувані значення, підвищити надійність; для принципово динамічних даних використовувати регулярні вирази;
6. **Verification** — перезапустити тест після кожної правки;
7. **Iteration** — повторювати, доки тест не пройде чисто.

Принципи: лікувати **по одному** падінню за раз, документувати хід думки, надавати перевагу надійному рішенню над «швидким хаком», і — важливе — якщо помилка не зникає, а впевненість у правильності тесту висока, позначати тест як `test.fixme()`.

### Вхід і вихід

- **Вхід:** ім'я тесту, що падає.
- **Вихід:** тест, що проходить, **або** пропущений тест, якщо хілер вважає, що зламана сама функціональність.

Ось це останнє — найцінніше в дизайні. У хілера є **право сказати «застосунок зламано»**, а не «підігнати тест під баг». Хілер, який завжди домагається зеленого, — це не хілер, а генератор хибно-позитивних результатів.

### Як це виглядало у тебе (реальний кейс)

Коли ти проходив цикл вручну на GreenKart, падіння були саме «хілерського» типу:

| Падіння | Першопричина | Патч |
|---|---|---|
| `toContainText('₹ 120')` не проходить | символ `₹` вставляється CSS-ом (`::before`), у тексті DOM його немає | перевіряти класи `.quantity` / `.amount` |
| `getByText(/No\. of Items : 1/)` не знайдено | підсумки розбиті за елементами з множинними пробілами | асерти за класами `.totAmt`, `.discountAmt`, `.promoInfo` |
| Після «Proceed» тест падає на редіректі | екран підтвердження живе >5 с, потім авто-редірект на `#/` | асерт тексту підтвердження + `toHaveURL(/#\/$/, { timeout: 15000 })` |

Щоразу ти робив рівно те, що робить хілер: відтворював, оглядав UI, знаходив першопричину, патчив, перезапускав. Різниця лише в тому, що тепер це вміє агент — **але рішення все одно потребують твоєї голови під час рев'ю**.

## 8. Артефакти та конвенції (відео, 4:39)

Структура, яку створює й підтримує цикл (з документації):

```bash
repo/
  .github/                    # agent definitions (визначення агентів)
  specs/                      # human-readable test plans (плани для людей)
    basic-operations.md
  tests/                      # generated Playwright tests (тести)
    seed.spec.ts              # seed test for environment (затравочний тест)
    tests/create/add-valid-todo.spec.ts
  playwright.config.ts
```

| Артефакт | Хто створює | Навіщо | Правило супроводу |
|---|---|---|---|
| `.github/agents/*.md` | `init-agents` | визначення агентів = інструкції + MCP-інструменти | регенерувати при оновленні Playwright |
| `specs/*.md` | planner | план: кроки, очікування, дані; стартує від seed | людиночитаний, але точний; правиться людиною |
| `tests/seed.spec.ts` | людина | готовий `page`-контекст для завантаження середовища | точка входу для всіх сценаріїв |
| `tests/**/*.spec.ts` | generator (+ healer) | виконувані тести, один до одного зі сценаріями | один тест на файл, `describe` = група плану |
| `playwright.config.ts` | людина | конфігурація запуску | не чіпається агентами |

Ключова думка з документації: плани **можна починати з нуля або розширювати від seed-тесту**, а тести вирівнюються **один до одного зі спеками, де це можливо**. Ця однозначна зв'язка «сценарій ↔ файл» згодом дозволяє хілеру точково лікувати один тест, не зачіпаючи решту.

## 9. Наскрізний сценарій повністю

Так виглядає правильна послідовність (зістав із главами відео):

```bash
# 1. Оновити Playwright і розкласти визначення агентів
npm install -D @playwright/test@latest
npx playwright init-agents --loop=vscode        # або claude / codex / opencode
```

2. **Підготувати seed** — `tests/seed.spec.ts` + `tests/fixtures.ts` (0:52).
3. **Покликати planner**: у промпті — мета + seed-файл. Отримати `specs/*.md` (2:15).
4. **Покликати generator**: у промпті — файл плану. Отримати `tests/**/*.spec.ts` (3:11).
5. **Запустити тести**, ті, що впали, — віддати healer'у за іменем (4:16).
6. **Перевірити й відрев'юїти** результат: план, тести, звіт (4:39).

Крок 6 не можна пропускати: агенти залишають артефакти, але **відповідальність за їхню якість — на тобі**. План може бути поверхневим, тест — перевіряти не те, хілер — «полагодити» тест під змінене (але неправильне) поводження застосунку.

> 🔧 **Варіант для DSH.** Кроки 1, 3, 4 і 5 у DSH виглядають інакше: визначення агентів беруться не з `.github/agents/`, а оформлюються як **скіли DSH**; MCP-сервер `playwright-test` підключається рядком у конфізі профілю DSH, а не через `.vscode/mcp.json`. Детальне покрокове налаштування — в [Уроці 2](02-agents-in-dsh.md).

## 10. Підводні камені

1. **Забули регенерувати визначення.** Оновив Playwright — запусти `init-agents` заново, інакше агенти працюють старими інструментами.
2. **Немає seed — немає циклу.** Без затравочного тесту планувальник не зможе привести застосунок у потрібний стан і буде досліджувати «не той» застосунок.
3. **Один тест на файл — не бюрократія.** Це контракт із хілером: одне падіння = один файл = одна правка.
4. **Описи груп та імена сценаріїв мають збігатися з планом дослівно.** Саме за цими рядками генератор пов'язує план і код.
5. **Не дозволяй хілеру «підганяти» тест під баг.** Якщо функціональність зламана — правильний результат `test.fixme()` і баг-репорт, а не зелений тест.
6. **VS Code старої версії** — агентний досвід не запрацює: потрібна 1.105+ (для VS Code).
7. **Плани потрібно читати.** Markdown-план — єдине місце, де ти можеш дешево зловити помилку до того, як вона перетвориться на код.

## 11. Практика на твоєму проєкті (`playwright-DSH-plan-gen-heal`)

Ти вже пройшов цикл вручну на GreenKart — тепер запусти його агентами та порівняй результати.

**Вправа 1. Порівняй плани.**
Відкрий `specs/greenkart.plan.md` і запусти planner на тому самому застосунку
(https://rahulshettyacademy.com/seleniumPractise/#/). Порівняй: що агент знайшов такого, чого немає в твоєму плані? Які твої сценарії він упустив? Найімовірніше, він додасть негативні кейси (порожній пошук, невалідні дані) — перевір.

**Вправа 2. Порівняй тести.**
Візьми одну групу (наприклад, `Shopping Cart`) і згенеруй тести агентом. Порівняй зі своїми файлами з `tests/cart/`: які локатори обрав генератор, чи додав він `expect` там, де ти їх забув.

**Вправа 3. Зламай і вилікуй.**
Спеціально зіпсуй локатор в одному тесті (наприклад, заміни `.totAmt` на `.totAmt-old`) і віддай тест хілеру. Зафіксуй: чи знайшов він причину, чи був патч мінімальним, чи не зламав він сусідні тести.

## 12. Питання для самоперевірки

1. Чим принципово відрізняється результат роботи агента від результату роботи MCP-сервера?
2. Чому планувальник **запускає** seed-тест, а не просто читає його?
3. Що саме генератор бере з живого браузера, чого не зміг би взяти «з голови»?
4. У якому випадку правильний вихід хілера — не зелений, а пропущений тест?
5. Чому визначення агентів потрібно регенерувати при оновленні Playwright?
6. Що станеться зі зв'язкою «план ↔ тест», якщо перейменувати сценарій у плані й не перегенерувати тест?

# Урок 2. Агенти Playwright у DeepSeek Harness

> **Навіщо цей урок.** В [Уроці 1](01-intro-test-agents.md) усе викладено за офіційними матеріалами Playwright — а там цільові платформи називаються Claude Code, GitHub Copilot, Codex і OpenCode. Жодна з них не твоя: твоє середовище — **DeepSeek Harness (DSH)**. Модель `Claude Sonnet 4.6` з визначення агента тобі недоступна й не потрібна. Цей урок показує, як отримати **той самий цикл** planner → generator → healer засобами DSH.
>
> Джерела: файли та документація пакетів DSH у `C:\Users\vital\AppData\Roaming\npm\node_modules\@deepseek-ai\dsh\`, твій профіль `C:\Users\vital\.dsh\`, вихідники Playwright у `node_modules/playwright/lib/`.

## 1. Чому не можна просто «покласти файли як є»

Команда `npx playwright init-agents --loop=vscode` (вона ж `copilot`) створює в проєкті чотири артефакти. Перевіримо кожен: чи читає їх DSH?

| Артефакт `init-agents` | Для кого створено | Чи читає DSH |
|---|---|---|
| `.github/agents/playwright-test-*.agent.md` | GitHub Copilot / VS Code | ❌ ні |
| `.github/prompts/*.prompt.md` | Copilot (флаг `--prompts`) | ❌ ні |
| `.vscode/mcp.json` | VS Code | ❌ ні |
| `.github/workflows/copilot-setup-steps.yml` | CI для Copilot-агента | ❌ ні (для DSH це просто файл) |

DSH — самостійний харнес зі своєю конфігурацією. Він **не читає** ні `.vscode/mcp.json`, ні `.github/agents/`. Але це не означає, що робота пропала: переноситься **зміст**, а не формат. З чотирьох файлів нам потрібні:

1. текст інструкцій трьох агентів (те, що лежить після frontmatter у `.agent.md`);
2. список дозволених MCP-інструментів (поле `tools:`);
3. сам MCP-сервер — команда `npx playwright run-test-mcp-server`;
4. конвенції артефактів: `specs/`, `tests/`, `seed.spec.ts` — вони від платформи не залежать взагалі.

## 2. Три механізми DSH, які замінюють «агентів»

| Що потрібно | Механізм DSH | Де живе | Чим є |
|---|---|---|---|
| Інструменти браузера й тестів | **MCP-клієнт** | профіль: `~/.dsh/profiles/web/cordis.patch.yml` | plugin-row `@deepseek-ai/dsh-mcp-client` |
| Інструкції ролі («ти планувальник») | **Скіл** | `<проєкт>/.agents/skills/<ім'я>/SKILL.md` або `~/.dsh/skills/<ім'я>/SKILL.md` | markdown із frontmatter |
| Власна збірка агента повністю (інструменти + промпт) | **Preset** | `~/.dsh/.agent-presets/<id>/agent.cordis.yml` | список plugin-row (копія стандартного) |

Плюс окремо — **модель і reasoning effort**: у DSH вони задаються налаштуваннями (`~/.dsh/settings.yaml`) і вибором у GUI, а не полем `model:` у визначенні агента. Твій поточний конфіг:

```yaml
# ~/.dsh/settings.yaml
agent-default-model:
  provider: deepseek-official
  model: deepseek-v4-flash
  reasoningEffort: max
```

**Що це означає на практиці:** «агент Playwright» у DSH — це **скіл із роллю** плюс **підключений MCP-сервер**. Жодного `model: Claude Sonnet 4.6` у цій схемі немає і бути не повинно.

## 3. Крок 1. Підключити MCP-сервер `playwright-test`

### Що в тебе вже є

У твоєму профілі DSH уже підключено браузерний Playwright MCP — саме тому в мене в цій сесії доступні інструменти вигляду `mcp__playwright__browser_click`:

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml  (поточний вміст)
- insert:
    - id: mcp-playwright
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: playwright
        transport: stdio
        command: npx.cmd
        args: ['-y', '@playwright/mcp@latest']
```

Це **загальний** браузерний MCP (`@playwright/mcp`). Він уміє навігувати, клікати, знімати снапшоти — тобто вміє все, що потрібно для *дослідження*. Але в нього **немає** спеціалізованих інструментів агентів: `planner_save_plan`, `generator_write_test`, `test_run`, `test_debug`.

### Чого бракує

Ті самі інструменти дає **інший** сервер — `playwright run-test-mcp-server` (у CLI Playwright це *прихована* команда: у `--help` її не видно, але вона існує). Саме її Playwright прописує в усі свої конфіги агентів.

Додай другий рядок у той самий файл:

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml
- insert:
    - id: mcp-playwright
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: playwright
        transport: stdio
        command: npx.cmd
        args: ['-y', '@playwright/mcp@latest']

    - id: mcp-playwright-test
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: playwright-test
        transport: stdio
        command: npx.cmd
        args: ['playwright', 'run-test-mcp-server']
        cwd: 'C:\Users\vital\AI\playwright-DSH-plan-gen-heal'
```

Три деталі, які важливі саме тут:

- **`cwd` обов'язковий за змістом.** Сервер тестів працює в контексті проєкту: йому потрібні `playwright.config.ts`, `specs/`, `tests/`. Без `cwd` він запуститься в каталозі процесу DSH і не знайде проєкт.
- **`serverName` задає імена інструментів.** Конвенція DSH — `mcp__<serverName>__<rawName>`. Отже, ти отримаєш `mcp__playwright-test__planner_save_plan`, `mcp__playwright-test__test_run` і так далі. Ім'я має бути унікальним і підходити під `[A-Za-z0-9_-]{1,32}` — `playwright-test` підходить.
- **`npx.cmd`, а не `npx`** — на Windows інакше не запуститься (у тебе в наявному рядку вже так). Якщо `npx` у системі вередує, є резервний варіант: `command: node`, `args: ['node_modules/playwright/cli.js', 'run-test-mcp-server']` разом із тим самим `cwd`.

Правка файлу профілю застосовується **без перезапуску**: MCP-клієнт DSH перепідключає сервер за фактом зміни (hot-swap), і набір інструментів замінюється повністю — без дублів.

### Як перевірити, що вийшло

1. Після правки почни нову сесію в потрібному проєкті.
2. Спроси: *«Які інструменти починаються з `mcp__playwright-test__`?»* — або просто попроси скласти план: агент має побачити `planner_setup_page` і `planner_save_plan`.
3. Якщо інструментів немає — дивись логи DSH: помилка підключення MCP пишеться в лог (`reconnecting` / `final failure` із числом спроб).

> ⚠️ Інструменти MCP видимі моделі **постійно**, доки сервер підключено, і їхні схеми витрачаються на кожному запиті. У токен-метрі DSH це стаття «Tools». Якщо сервер потрібен не завжди — тримай його в окремому профілі або вимикай рядок, коли не працюєш із тестами.

## 4. Крок 2. Оформити три ролі як скіли DSH

### Куди DSH дивиться в пошуку скілів

Провайдер `dsh-skill-filesystem` сканує корені в такому порядку пріоритету:

| Ранг | Джерело | Шлях |
|---|---|---|
| 100 | project-dsh | `<проєкт>/.dsh/skills` |
| 200 | project-agents | `<проєкт>/.agents/skills` |
| 300 | custom | задається конфігом |
| 400 | user-dsh | `~/.dsh/skills` |
| 500 | user-agents | `~/.agents/skills` |

Де `<проєкт>` — найближчий предок із `.git`.

**Приємний збіг:** інсталятор скілів Playwright уміє писати рівно в `.agents/skills` — це режим `npx playwright init-skills --loop=agents` (перевірено за вихідником: шлях збирається як `.<target>/skills/<skill>`). Тобто Playwright і DSH уже сходяться на одній конвенції `.agents/skills` — і три твоїх рольових скіли логічно покласти туди ж, поряд з уже встановленими `playwright-cli`, `playwright-component-testing`, `playwright-trace` (вони в тебе вже є — саме вони перелічені в каталозі скілів поточної сесії).

### Формат скіла

Скіл — це або папка `<ім'я>/SKILL.md`, або плоский файл `<ім'я>.md`. Frontmatter:

```yaml
---
name: kebab-case-ім'я          # обов'язково
description: ...              # обов'язково — потрапляє в каталог, за ним модель вирішує, чи потрібен скіл
whenToUse: ...                # опційно
disable-model-invocation: false   # опційно: true — скіл недоступний моделі
user-invocable: true              # опційно: false — скіл недоступний людині
---
```

### Готові шаблони трьох ролей

Створи три папки в `<проєкт>/.agents/skills/`. Тіла написані за мотивами реальних інструкцій із `.github/agents/*.agent.md`, але з іменами інструментів у DSH-форматі.

**`.agents/skills/playwright-test-planner/SKILL.md`**

```markdown
---
name: playwright-test-planner
description: Складає Markdown-план тестування вебзастосунку — досліджує інтерфейс браузерними інструментами та зберігає план у specs/. Використовувати, коли потрібен тест-план або повне покриття сценаріїв.
whenToUse: Користувач просить дослідити застосунок і скласти план тестування.
---

Ти — експерт із планування тестування вебзастосунків.

Порядок роботи:
1. Визнач seed-тест (зазвичай `tests/seed.spec.ts`) і запусти його — так виконуються
   global setup, залежності проєкту та всі фікстури.
2. Один раз виклич `mcp__playwright-test__planner_setup_page`, далі досліджуй інтерфейс
   інструментами `mcp__playwright-test__browser_*`. Скриншоти — лише за потреби,
   снапшот інформативніший.
3. Склади карту користувацьких потоків і критичних шляхів.
4. Спроєктуй сценарії: happy path, крайові випадки, обробка помилок.
5. Збережи план інструментом `mcp__playwright-test__planner_save_plan` у `specs/<ім'я>.md`.

Вимоги до плану:
- групи (`###`) і сценарії (`####`) з нумерацією;
- для кожного сценарію: Steps, Expected Results, посилання на Seed;
- стартовий стан завжди вважається чистим;
- кроки конкретні настільки, щоб їх виконав будь-який тестувальник;
- обов'язкові негативні сценарії;
- сценарії незалежні та запускаються в будь-якому порядку.

Ніколи не пиши тести — твій артефакт лише план.
```

**`.agents/skills/playwright-test-generator/SKILL.md`**

```markdown
---
name: playwright-test-generator
description: Перетворює Markdown-план із specs/ на виконувані Playwright-тести, перевіряючи селектори й асерти наживо в браузері. Використовувати, коли є план і потрібні тести.
whenToUse: Є план у specs/, і потрібно згенерувати за ним тести.
---

Ти — генератор Playwright-тестів. Ти НЕ пишеш код із пам'яті: кожен крок спочатку
виконується наживо, і лише потім стає кодом.

Порядок роботи для кожного сценарію плану:
1. `mcp__playwright-test__generator_setup_page` — підняти сторінку сценарію.
2. Для кожного кроку: виконати дію живими інструментами
   (`browser_click`, `browser_type`, `browser_navigate`, ...), використовуючи текст кроку
   як намір. Перевірки робити `browser_verify_*`.
3. `mcp__playwright-test__generator_read_log` — забрати лог того, що реально спрацювало.
4. Одразу `mcp__playwright-test__generator_write_test` — записати вихідний код із лога.

Правила оформлення:
- один тест на файл, ім'я файлу — kebab-case ім'я сценарію;
- `test.describe(...)` збігається з групою верхнього рівня з плану;
- заголовок тесту збігається з іменем сценарію з плану;
- у шапці файлу — `// spec: specs/<файл>.md` і `// seed: tests/seed.spec.ts`;
- перед кожним кроком — коментар із текстом кроку (не дублювати при кількох діях);
- локатори — рольові (`getByRole`, `getByLabel`), а не CSS-ланцюжки;
- динамічні дані перевіряти регулярними виразами.

Не «покращуй» план: якщо крок незрозумілий — повідом про це, а не вигадуй поведінку.
```

**`.agents/skills/playwright-test-healer/SKILL.md`**

```markdown
---
name: playwright-test-healer
description: Запускає набір тестів і лікує тести, що падають — відтворює кроки, оглядає UI, знаходить першопричину й патчить тест. Використовувати при падіннях Playwright-тестів.
whenToUse: Тести падають, і потрібно знайти та усунути причину.
---

Ти — інженер із налагодження Playwright-тестів. Працюй методично, по одному падінню за раз.

Порядок роботи:
1. `mcp__playwright-test__test_run` — запустити набір, знайти тести, що падають.
2. `mcp__playwright-test__test_debug` — для кожного падіння запустити налагодження.
3. На паузі на помилці: вивчити деталі, зняти снапшот (`browser_snapshot`), подивитися
   консоль і мережу, знайти актуальний локатор (`browser_generate_locator`).
4. Визначити першопричину: селектор, що змінився, проблема синхронізації, залежність
   від даних, зміна в застосунку, яка зламала припущення тесту.
5. Виправити код тесту — мінімальною правкою.
6. Перезапустити тест і переконатися, що він проходить.
7. Повторювати до чистого проходження.

Правила:
- лікувати по одному падінню за раз;
- пояснювати, що було зламано і чому правка саме така;
- надавати перевагу надійному рішенню над швидким хаком;
- НЕ підганяти тест під баг. Якщо функціональність справді зламана — позначити
  тест як `test.fixme()` і повідомити про це, а не робити його зеленим.
```

> 💬 **Про мову тіла скіла.** Тіло скіла читається моделлю при кожному завантаженні, тому воно витрачає токени. Якщо захочеш економії — тримай тіла англійською: за нашими вимірами російський текст коштує приблизно в 1,5–2 раза дорожче (див. розділ про токенізацію в уроці 1). Frontmatter краще залишити читабельним для себе.

## 5. Крок 3 (опційно). Preset для «режиму Playwright-агентів»

**Preset** у DSH — це папка `~/.dsh/.agent-presets/<id>/agent.cordis.yml` зі списком plugin-row: повна збірка агента (інструменти + розділи системного промпту). Механічно це найближче до того, чим є визначення агентів у Copilot, але значно важче.

Що важливо знати, перш ніж іти цим шляхом:

- **Авторинг лише копіюванням.** Новий preset створюється копією наявного (через сервіс/сторінку налаштувань), а далі правиться файл композиції. Створювати «з нуля» текстом не передбачено.
- **Preset обирається на сесію**, і перемикати його можна лише в сесії, яка ще нічого не зробила (порожньої). Зміна композиції посеред розмови заборонена: в історії залишилися б виклики інструментів, яких у новій збірці немає.
- **Субагенти успадковують preset батька** (`composeFrom`), а не обирають свій. Отже, роздати три ролі «типами субагентів» у DSH **не можна** — роль передається скілом або текстом промпту. Це ключова відмінність від Claude Code, де субагент — окреме визначення з власною моделлю.

**Висновок:** для трьох ролей Playwright достатньо скілів (крок 2). Preset варто робити, лише якщо хочеться вмикати весь режим одним перемикачем — наприклад «лише Playwright-тести, без решти інструментів».

## 6. Як виглядає цикл у DSH: готові промпти

Налаштування зроблено — тепер сам цикл. У DSH роль запитується **явним завантаженням скіла** в промпті.

**Планувальник:**

> Завантаж скіл `playwright-test-planner`. Досліди https://rahulshettyacademy.com/seleniumPractise/#/ і склади план тестування в `specs/greenkart-agents.plan.md`. Seed-тест — `tests/seed.spec.ts`. Покрий пошук товарів, кошик, промокоди, оформлення замовлення і Top Deals, включно з негативними сценаріями.

**Генератор:**

> Завантаж скіл `playwright-test-generator`. Візьми план `specs/greenkart-agents.plan.md` і згенеруй тести за групою «Shopping Cart» у `tests/cart-agents/`. Один тест на файл, `describe` — як у плані.

**Хілер:**

> Завантаж скіл `playwright-test-healer`. Запусти `tests/cart-agents/`, знайди тести, що падають, і полагодь їх. Якщо вважаєш, що зламана функціональність застосунку — познач тест `test.fixme()` і поясни чому.

Прийом, який економить контекст: **кожен крок циклу — окрема сесія DSH**. Планувальник залишає `specs/*.md`, генератор — `tests/*.spec.ts`; артефакти на диску і є передачею роботи. Тоді історія досліджень не тягнеться в сесію генерації.

## 7. Що переноситься без змін

Усе, що стосується конвенцій, від платформи не залежить — це найцінніша частина офіційної схеми:

| Артефакт | Роль | Актуальний у DSH |
|---|---|---|
| `tests/seed.spec.ts` + `tests/fixtures.ts` | вхідна точка середовища | ✅ так, без змін |
| `specs/*.md` — групи, сценарії, Steps, Expected Results | план для людей | ✅ так, формат той самий |
| один тест на файл | контракт із хілером | ✅ так |
| `describe` = група плану, заголовок = ім'я сценарію | зв'язок план ↔ тест | ✅ так |
| шапка `// spec:` і `// seed:` | трасованість | ✅ так |
| коментар із текстом кроку перед дією | читабельність | ✅ так |

## 8. Підводні камені саме в DSH

1. **`.vscode/mcp.json` і `.mcp.json` DSH ігнорує.** Єдина точка підключення MCP — профіль DSH (`cordis.patch.yml`), окремий plugin-row на кожен сервер.
2. **Забути `cwd` у `playwright-test`.** Сервер мовчки підніметься не в тому каталозі, і інструменти плану/тестів не знайдуть проєкт.
3. **`run-test-mcp-server` не видно в `--help`.** Це прихована команда; її відсутність у довідці не означає, що її немає.
4. **Роль не можна «видати» субагенту.** Субагент у DSH успадковує композицію батька, тому роль передається скілом у промпті, а не типом агента.
5. **`model:` із `.agent.md` — мертве поле.** Модель і reasoning effort задаються в DSH (`settings.yaml` і вибір у GUI). Не намагайся «привести визначення до ладу», правлячи це поле — файли все одно перегенеруються.
6. **Інструменти MCP витрачають контекст постійно.** Кожен підключений сервер віддає схеми інструментів на кожен запит — це видно в токен-метрі. Тримай підключеним лише те, що потрібно зараз.
7. **Скіли видно після встановлення не миттєво «в голові», а в каталозі.** Тіло читається в момент завантаження скіла, тому правки підхоплюються одразу; а ось поява/зникнення самих скілів відстежується спостерігачем каталогу.
8. **План і тести — це файли, а не чат.** Якщо робота зроблена лише «в розмові», наступний крок циклу не зможе її підхопити.

## 10. Вправа

Візьми **один** сценарій із уже готового плану — наприклад `TC-2.1 should add single product to cart` — і запусти його циклом у DSH:

1. **План:** попроси планувальника скласти план лише для групи «Shopping Cart» і зберегти в `specs/cart-agents.plan.md`. Порівняй зі своїм `specs/greenkart.plan.md`: що агент додав, що втратив.
2. **Тест:** попроси генератора зробити тести за цим планом у `tests/cart-agents/`. Порівняй локатори зі своїми з `tests/cart/`.
3. **Лікування:** заміни в одному згенерованому тесті локатор на вочевидь неправильний (наприклад `.totAmt` → `.totAmt-old`) і віддай хілеру. Перевір: чи мінімальна правка, чи пояснив він першопричину, чи не зачепив сусідні тести.
4. **Висновок:** запиши в `SESSION-NOTES.md` проєкту, чим цикл під агентами відрізняється від твого ручного проходу.

## 11. Джерела уроку

**Внутрішні (файли твого середовища):**

- `~/.dsh/profiles/web/cordis.patch.yml` — підключення MCP-серверів у DSH.
- `~/.dsh/settings.yaml` — модель за замовчуванням і reasoning effort.
- `@deepseek-ai/dsh-mcp-client` (README) — конфігурація MCP: `serverName`, `transport`, `command`, `args`, `cwd`, перепідключення, конвенція імен `mcp__<serverName>__<rawName>`.
- `@deepseek-ai/dsh-skill-filesystem` (README) — корені пошуку скілів і формат `SKILL.md`.
- `@deepseek-ai/dsh-agent-presets` (README) — пресети, їх авторинг і успадкування субагентами.
- `node_modules/playwright/lib/agents/generateAgents.js` — що саме пише `init-agents` у кожному циклі.
- `node_modules/playwright/lib/program.js` — список циклів `init-agents`, прихована команда `run-test-mcp-server`, команда `init-skills`.
